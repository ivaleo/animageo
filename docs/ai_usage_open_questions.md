# AI-usage: открытые вопросы

Список нерешённых вопросов, всплывших при разработке и валидации гайда для
сторонних ИИ (`animageo/AI_USAGE_PROMPT.md`, 1.4.5). Валидация — 6 прогонов
агентов без контекста (nine-point circle, incircle, парабола, касательные,
параллелограмм, вписанный угол). Каждый пункт — реальный шов в API, который
агенты обходили руками; гайд документирует обход, но нативная поддержка была
бы чище.

## 1. DSL-точки не keyframe-независимы (главный)

`play_keyframes` работает несимметрично между GGB- и DSL-сценами:

- **GGB**: свободная точка из `.ggb` — элемент без создающей команды →
  `get_independents()` её видит → в keyframes пишется `"A": [x, y]`.
- **DSL**: `A = Point(0, 0)` — это команда `Point` в графе (узел с
  литеральными аргументами). Есть создающая команда → под текущий критерий
  независимости (`level == 0 and not input_commands`) не попадает,
  `get_independent_elements()` возвращает `{}`, `play_keyframes({"values":
  {"A": [1, 2]}})` падает с `'A' is not an independent element`.

**Обход (в гайде §8.3):** прогонять координаты через переменные —
`cx = addVar('cx'); putCode('A = Point(cx, cy)')`, анимировать `cx`/`cy`.

**Что сделать:** научить `get_independents()` (в
`geo/construction.py`) распознавать точку, созданную командой `Point`
**только из числовых литералов** (не из переменных, не point-on-object),
отдавать её как `free_point`; при применении keyframe-значения — обновлять
аргументы этой команды и метить зависимых на rebuild. Тогда один и тот же
keyframes-JSON работает для GGB и DSL одинаково.

**Дизайн-решения:** критерий «свободности» (`Point(2, 3)` — да;
`Point(cx, cy)` — нет, уже var-driven; точка на кривой — это tparam-point);
распространять ли на числа (`x = 5` в DSL); не сломать web-клиентский
контракт `get_independents()` (там завязан UI кейфреймов).

## 2. Кривые (Conic/Function/Parabola) не являются препятствием для label-солвера

Экс-агент (парабола): подпись точки `P` на параболе солвер поставил прямо на
кривую — `Function`/`Conic` не регистрируются как obstacle в
`label_placement`. Обход: ручной `label_offset_px` + `label_placement_locked`.
**Что сделать:** добавить сэмплированную кривую в `_collect_obstacles`
(как сегменты/окружности), чтобы подписи точек на кривой её огибали.

## 3. Value-подписи полигона (площадь) не разводятся солвером

Экс-агент (параллелограмм): подпись площади полигона якорится в центроиде;
если там именованная точка (точка пересечения диагоналей), подписи
накладываются, а `autoPlaceLabels` полигональные value-подписи не разводит
(таблица солвера покрывает Point/Segment/Angle). Обход: ручной
`label_offset_px` + `label_placement_locked`. **Что сделать:** включить
полигональные value-подписи в разводку солвера, либо якорить их в
свободном секторе, а не строго в центроиде.

## 4. `fitView` не пере-центрирует под движение

`fitView` кадрирует по видимой статике. Если анимация уводит геометрию, кадр
покрывает самый широкий охват, но финальное состояние может оказаться не по
центру (экс-агент с касательными: точка в ближнем положении ушла в левую
половину). Всё остаётся в кадре, но не отцентровано. **Что сделать
(опц.):** режим `fitView(..., motion_hint=[...])` или авто-паддинг под
заявленный диапазон движения.

## 5. Отдельный: conic-line intersection index order

Не про AI-usage, но зафиксирован в этом же цикле — см.
[TZ-conic-line-intersection-index-order.md](TZ-conic-line-intersection-index-order.md).
`Intersect(коника, …, n)` не сохраняет порядок GeoGebra на вырожденных
углах (вершина «прыгает» на другую ветвь). Реальный баг корректности,
приоритет средний.
