## 0. Базовая аналитика: как устроен экспорт сейчас

### 0.1 Два независимых тракта вывода

В проекте уже сосуществуют два принципиально разных способа получить файл:

1. **Статический тракт (vector «снимок»).** `AnimaGeoScene` строит mobjects в
   `construct()`, после чего метод сериализует *текущий кадр*:
   - `exportSVG(filepath)` (`animageo.py:1416`) — обходит `self.mobjects`,
     прогоняет каждый VMobject через `_create_svg_from_vmobject_internal`
     (`parsers/svg_parser.py`) и пишет в `cairo.SVGSurface`.
   - `exportTikZ(...)` (`animageo.py:1432`) — семантический экспортёр
     `exporters/tikz/` (обходит элементы в z-порядке, печатает нативные
     `\draw`/`\node`).
2. **Рендер-тракт (растровое видео/кадр).** Анимация делается вызовами
   `self.play(...)` (в т.ч. `play_keyframes`), а файл пишет **сам manim**
   (`SceneFileWriter` + ffmpeg). Формат контейнера задаёт `manim.config.format`,
   из коробки доступны `png | gif | mp4 | webm | mov` (проверено: `manim render
   --help`).

Новые форматы ложатся на эти тракты так:

| Формат | Тракт | Базируется на |
|--------|-------|---------------|
| PDF, EPS | статический | `svg_parser.py` (смена cairo-surface) |
| GIF, WebM, MOV | рендер | `manim.config.format` |
| animated SVG | статический ×N кадров | цикл из `_play_keyframe_interval` + `svg_parser.py` |
| JSXGraph / JS | новый (транспиляция графа) | `construction` + `get_independents()` + `resolver` |
| accessible SVG | новый (native-`<text>` SVG) | семантический граф + `resolve_label_text` |

### 0.2 Юнит-модель (нужна для PDF/EPS и animated SVG)

`style.export` несёт всё необходимое:

```python
style.export = {
    'ptUnit':       <px на 1 math-unit (MU) в финальном холсте>,
    'ptWidth', 'ptHeight':  <размер холста в px>,
    'ptXZero', 'ptYZero':   <сдвиг начала координат, px>,
    'ptUnit_style': <масштаб для штрихов/шрифтов>,   # _style_ptUnit()
    'ptUnit_ggb':   <исходный GGB px/MU для смещений подписей>,
    'fontSize':     <GGB px шрифта, опционально>,
}
```

SVG-CTM (`_get_cairo_context`): `Matrix(ptUnit, 0, 0, -ptUnit, ptXZero, ptYZero)`
— MU → px, ось Y инвертирована. Холст `ptWidth × ptHeight` px.

### 0.3 Критичные факты, влияющие на дизайн

- **Подписи — это векторные контуры, а не текст.** `create_label` строит
  `Tex/MathTex`, который Cairo пишет как `<path>` Безье. Следствия:
  - PDF/EPS: текст будет «кривыми» (невыделяемый, непоиск­иваемый) — это норм
    для печати, но это же причина, по которой accessible SVG нельзя получить из
    текущего SVG-пути (в нём *нет* машиночитаемого текста вообще).
  - JSXGraph/TikZ заново эмитят текст подписи через `resolve_label_text(scene,
    elem)` (`labels.py`) — не из контуров.
- **Стиль читается единообразно** через `style.resolver.resolve(scene, elem,
  key, default=...)`. Любой новый эмиттер обязан ходить туда же, иначе GGB-импорт
  / overlay / `elem.style` разъедутся с рендером.
- **Граф конструкции даёт топологический порядок и зависимости.**
  `construction.state[name]['outputs']`, `['level']`, `['input_commands']` +
  `get_independents()` — это ровно то, что нужно для (а) транспиляции в JS с живыми
  связями и (б) разделения «статическое/динамическое» в animated SVG.
- **`get_independents()`** возвращает анимируемые входы с типами:
  `free_point` (coords), `tparam_point` (constraint ∈ {circle, segment, ray,
  line}, tparam, coords), `number`, `measure`, `angle`, `boolean`.

## 1. PDF / EPS — детальный план  ·  сложность: низкая

### 1.1 Цель и аудитория
Векторный однофайловый рисунок для печати, вставки в LaTeX (`\includegraphics`),
подачи в журналы (Elsevier/Springer принимают PDF и EPS для векторной графики).
Тот же визуал, что у SVG, в формате, который ждут «по умолчанию».

### 1.2 Точка переиспользования
`parsers/svg_parser.py` уже умеет всё: обход семейства VMobject, Безье,
stroke/fill/cap/join, фон. Меняется **только тип cairo-surface**. Cairo 1.18.4 в
среде: `PDFSurface`, `PSSurface`, `PSSurface.set_eps(True)` — все доступны.

### 1.3 Главная (и единственная) тонкость — единицы
- `SVGSurface` меряет в **px** (user unit ≈ CSS px).
- `PDFSurface`/`PSSurface` меряют в **типографских пунктах** (1 pt = 1/72").

Чтобы PDF выглядел так же, как SVG, при целевом `dpi` (по умолчанию 96 — как
`DEFAULT_DPI` в TikZ):

```
k = 72 / dpi                      # pt на «пиксель»
page = (ptWidth * k, ptHeight * k)            # размер страницы в pt
CTM  = Matrix(ptUnit*k, 0, 0, -ptUnit*k, ptXZero*k, ptYZero*k)
```

При `dpi=96`, `k=0.75`: холст 640×480 px → страница 480×360 pt ≈ 6.67"×5".

### 1.4 Реализация (шаги)
1. **`svg_parser.py` — обобщить surface.**
   ```python
   def _make_surface(kind, file_name, w_pt, h_pt):
       if kind == 'svg': return cairo.SVGSurface(file_name, w_pt, h_pt)
       if kind == 'pdf': return cairo.PDFSurface(file_name, w_pt, h_pt)
       if kind in ('ps', 'eps'):
           s = cairo.PSSurface(file_name, w_pt, h_pt)
           if kind == 'eps': s.set_eps(True)
           return s
       raise ValueError(kind)
   ```
   Расширить `_get_cairo_context(file_name, style, *, surface='svg', dpi=96.0)`:
   вычислить `k` (для `svg` → `k=1`), задать размер страницы и CTM с множителем
   `k`. `_paint_background` уже сурфейс-агностичен.
2. **Новые публичные хелперы** `create_pdf_from_vgroup` / `create_eps_from_vgroup`
   — тонкие обёртки над общим телом (или один `create_render_from_vgroup(...,
   surface=...)`). Обновить `__all__`.
3. **`animageo.py` — методы экспорта** рядом с `exportSVG`:
   ```python
   def exportPDF(self, filepath, *, dpi=96): ...
   def exportEPS(self, filepath, *, dpi=96): ...
   ```
   Тело идентично `exportSVG`, отличается аргументом `surface=`/`dpi=` и
   логом. Рекомендуется выделить приватный `_export_cairo(filepath, surface,
   dpi)` и сделать три публичных метода тонкими.
4. **(Опц.) Диспетчер** `export(self, filepath, *, format=None, **opts)` —
   инференс формата из расширения (`.svg/.pdf/.eps/.tex`); удобно для API и CLI.
5. **CLI (`__main__.py`).** Добавить в `--format` choices `pdf`, `eps`; в инференс
   из `-o` (`.pdf→pdf`, `.eps→eps`); собрать `export_call =
   self.exportPDF({output!r}, dpi=...)`. Добавить `--dpi` (общий для pdf/eps).

### 1.5 Риски / краевые случаи
- **EPS не поддерживает прозрачность.** Полупрозрачные заливки Cairo
  растеризует фолбэком → раздувание/потеря резкости. Решение: при экспорте в EPS,
  если в сцене есть `*_opacity < 1`, писать `logger.warning` и предлагать PDF/SVG;
  опционально флаг `flatten=True`. PDF прозрачность держит штатно.
- **Физический размер.** Документировать `--dpi`; дефолт 96 = визуальный паритет с
  TikZ/SVG. (Векторность означает, что в LaTeX размер всё равно зададут `width=`.)
- **Шрифты-кривые** — ожидаемо (как «text as shapes» в Inkscape/GeoGebra). Если
  когда-нибудь понадобится выделяемый текст — это отдельный не-Cairo путь
  (см. §5), вне рамок PDF/EPS.

### 1.6 Тесты (`tests/test_pdf_eps_export.py`)
- Рендер малой DSL/GGB-сцены → `exportPDF`/`exportEPS`.
- Проверка сигнатур: PDF начинается с `%PDF-1.`; EPS с `%!PS-Adobe-3.0 EPSF`.
- Ненулевой размер; для PDF — `MediaBox`/размер страницы соответствует
  `page = (ptWidth, ptHeight) * 72/dpi`.
- Ветка предупреждения о прозрачности в EPS.
- (Опц.) если есть `gs`/`pdfinfo` — структурная проверка.

### 1.7 Оценка
Низкая (~полдня + тесты/доки). Самый дешёвый и самый ожидаемый формат.

## 2. GIF (+ WebM / MOV) — детальный план  ·  сложность: низкая

### 2.1 Цель и аудитория
Универсальная анимация для чатов/писем/слайдов/README (GIF) и лёгкое
веб-видео с прозрачностью (WebM/MOV). Это **тот же растровый рендер, что и MP4**,
только другой контейнер.

### 2.2 Точка переиспользования
manim уже умеет всё это: `manim.config.format ∈ {png, gif, mp4, webm, mov}`. Наш
код анимации (`play_keyframes` → `_play_keyframe_interval`) выдаёт кадры в
`SceneFileWriter` без изменений.

### 2.3 Реализация (шаги)
1. **Программный переключатель формата.** Тонкий хелпер (модульная функция или
   `scene.setOutputFormat('gif')`), который перед рендером ставит
   `manim.config.format = fmt` (валидировать по множеству поддерживаемых). Это всё,
   что нужно на уровне API — никакого нового рендера.
2. **CLI — развести два трека.** Сейчас CLI делает только статический GGB→SVG/TikZ.
   Чтобы получить анимацию, нужен вход с keyframes:
   - добавить `--keyframes PATH` (JSON по формату `keyframes.py`);
   - расширить `--format` значениями `gif|mp4|webm|mov|png`;
   - в драйвере: если задан `--keyframes`, после `loadGGB` вызвать
     `self.play_keyframes(json.load(...))`; формат прокинуть в подпроцесс:
     `subprocess.run(['manim', driver, 'Scene_', '--format', fmt, ...])`.
   - Маршрутизация: `svg/tikz/pdf/eps` → export-метод (статический трек);
     `gif/mp4/webm/mov/png` → manim-рендер (рендер-трек). Без `--keyframes` и при
     видео-формате — выводится один кадр (last frame), это поведение manim.
3. **Прозрачность и качество.** Пробросить `--transparent` (manim) и `--fps`,
   `-q {l,m,h,p,k}`. Для GIF документировать ограничение палитры (256 цветов →
   возможный бандинг на градиентах/сглаживании); для плавных заливок советовать
   WebM/MOV (alpha + полноцвет).

### 2.4 Риски
- GIF-качество (палитра). manim/ffmpeg-цепочка фиксирована; тонкая настройка
  паль­литры (palettegen) — вне рамок, лишь документируем.
- CLI-«анимационный» трек — первое место, где CLI запускает реальную анимацию;
  убедиться, что драйвер-шаблон корректно сериализует путь к keyframes.

### 2.5 Тесты
- Smoke: сцена с 2 keyframes + `config.format='gif'` → файл с сигнатурой
  `GIF89a`; аналогично `webm` (EBML `0x1A45DFA3`). Guard на наличие manim/ffmpeg
  (`pytest.mark.skipif`).

### 2.6 Оценка
Низкая (~полдня). В основном CLI-плумбинг + хелпер + доки.

## 3. Animated SVG — исследование + план  ·  сложность: средняя/высокая

### 3.1 Суть проблемы (почему «осторожно»)
Наша анимация **не аффинна**: `play_keyframes` каждый кадр *пересобирает*
конструкцию (`geo.rebuild()`), т.е. зависимые точки/прямые/кривые
**пересчитываются** (точка едет по constraint, кривые ресэмплируются, дуги углов
перемасштабируются, подписи переезжают). Это нельзя выразить горсткой
`<animateTransform>` поверх статичных фигур: меняется сама геометрия и даже
топология путей (число подпутей при ресэмплинге кривой не постоянно).

Вывод: «честный» animated SVG = **векторный флипбук**, где каждый кадр —
настоящий статический SVG-рендер, а SMIL/CSS лишь переключает кадры. Это
гарантирует **попиксельное соответствие** manim (каждый кадр — реальный вывод
рендера), ценой размера файла.

### 3.2 Стратегия (v1): frame-baked SMIL/CSS «флипбук»
1. Взять цикл из `_play_keyframe_interval`, но **без manim**: использовать
   `apply_parsed_value` + `geo.rebuild()` (всё это уже без manim-зависимостей —
   см. `keyframes.apply_parsed_value`). Сэмплировать `N = ceil(duration*fps)`
   моментов времени с учётом easing интервалов.
2. На каждом сэмпле строить mobjects (как в `CreateMObject`) и сериализовать в
   **строку SVG** (Cairo `SVGSurface` умеет писать в file-like; завернуть в
   `io.BytesIO`). Получаем `N` SVG-фрагментов одинакового viewBox.
3. Собрать один SVG-документ: каждый кадр — `<g id="f{i}">` с управлением
   видимостью. Анимация:
   - **SMIL**: на каждой группе `<animate attributeName="display"
     values="none;inline;none" keyTimes=... dur="{T}s" repeatCount="indefinite"/>`
     (дискретное переключение по таймлайну). Это самый совместимый способ
     «листания» (Chrome/Firefox/Safari; не-IE).
   - **CSS-альтернатива**: `@keyframes` со `step()` по `opacity/display` — на
     случай окружений с урезанным SMIL.
4. Опции: `fps`, `loop` (`repeatCount`), `duration` (берётся из keyframes),
   `embed` (inline `<svg>` или отдельный файл), `frames` (жёсткий cap, чтобы не
   раздуть файл).

**Плюсы:** точное соответствие manim, масштабируемость, самодостаточность (без JS).
**Минусы:** размер файла растёт ~линейно с числом кадров × сложностью геометрии.

### 3.3 Оптимизация (v2): split «static / dynamic» по графу зависимостей
Большая часть конструкции на самом деле неподвижна. Из графа можно вычислить
множество «динамических» элементов = транзитивное замыкание `outputs` от
анимируемых независимых (`get_independents()` ∩ изменяемые в keyframes). Тогда:
- статические элементы эмитятся **один раз** (вне анимируемых групп);
- флипбук-кадры содержат только динамическое подмножество.

Это кратно уменьшает файл и опирается ровно на уже существующий
`construction.state[...]['outputs']`. Делать после рабочего v1.

### 3.4 Чего animated SVG принципиально не даёт (зафиксировать в доке)
- Морфинг атрибута `d` между кадрами по SMIL ненадёжен и не переживает смену
  топологии — поэтому именно флипбук, а не твининг отдельных путей.
- Интерактивность (перетаскивание) — это не animated SVG, а JSXGraph (§4).
- Рекомендация по применимости: короткие (≈≤5–8 с) и геометрически несложные
  сюжеты. Для длинных/тяжёлых — MP4/GIF (§2) или JS (§4).

### 3.5 Модульная раскладка
`exporters/animsvg/`: `options.py` (fps, loop, frames cap, embed, css|smil,
split), `frames.py` (бесmanim-цикл сэмплирования геометрии), `assemble.py`
(склейка кадров + SMIL/CSS-таймлайн), `exporter.py`. Вход — `KeyframeSequence`
(как `play_keyframes`). API: `scene.exportAnimatedSVG(filepath, keyframes, *,
fps=20, ...)`.

### 3.6 Тесты
- Сборка из 2-keyframe сцены: валидный XML, один `<svg>`, ровно `N` групп кадров,
  присутствуют `<animate>`/CSS-таймлайн, корректный `viewBox`.
- Идемпотентность размера: при `frames` cap число групп ограничено.
- (v2) проверка, что статический элемент эмитится один раз.

### 3.7 Оценка
Средняя/высокая (v1 ~1–2 дня: цикл сэмплинга + сборка SVG + таймлайн; v2 +0.5–1
день). Ниже, чем JSXGraph, т.к. переиспользует статический рендер и keyframe-цикл
и не требует портирования семантики.

## 4. JSXGraph / интерактивный JS — детальный план  ·  сложность: высокая (фазы)

### 4.1 Цель и аудитория
Не «картинка», а **живой виджет**: читатель тянет свободные точки/слайдеры — а
зависимая геометрия пересчитывается в браузере. Онлайн-учебники, LMS (Moodle),
сайты курсов. JSXGraph — кроссбраузерная HTML5-библиотека интерактивной геометрии
без плагинов, со своим constraint-движком и MathJax-подписями.

### 4.2 Ключевое отличие от TikZ (требует «думать внимательно»)
TikZ обходит **элементы** в z-порядке и печатает **статичные примитивы**.
JSXGraph должен обходить **команды** в **топологическом порядке** и создавать
элементы **через ссылки на родителей**, чтобы JS-граф связей повторял наш. То есть
центральная структура — не «эмиттер по типу элемента», а **`command_map`:
`Command → board.create(...)`**.

### 4.3 Идеальное соответствие, которое у нас уже есть
`get_independents()` транслируется в интерактивные входы 1:1:

| Наш тип | JSXGraph | Поведение |
|---------|----------|-----------|
| `free_point` | `board.create('point', [x,y])` | перетаскиваемая точка |
| `tparam_point` (constraint=circle/line/segment/ray) | `board.create('glider', [x,y, parent])` | **glider** по кривой |
| `number` / `measure` | `board.create('slider', ...)` | ползунок |
| `angle` | `slider` (рад/град) | ползунок угла |
| `boolean` | `checkbox` | переключатель |

Glider инициализируется текущими `coords` из `get_independents()` (JSXGraph
сам подберёт ближайший параметр на родителе).

### 4.4 Архитектура
Новый субпакет `exporters/jsxgraph/` по образцу tikz/:
- `options.py` — `JSXGraphOptions`: `boundingbox` (из `_get_scene_bounds`),
  `keepaspectratio`, `shownavigation`, `output ∈ {html, js, json}`, `mathjax`,
  `cdn_version`, `axis`.
- `context.py` — резолвер стиля + санитайзер имён (имена элементов → валидные JS
  идентификаторы, с картой) + форматирование JS-литералов.
- `style_map.py` — resolved style → атрибуты JSXGraph (`strokeColor`,
  `fillColor`, `strokeWidth`, `dash`, `size`, `face`, `fillOpacity`,
  `strokeOpacity`, `withLabel`, `name`). Цвета/толщины — через тот же `resolver`.
- `command_map.py` — **ядро**: `Command → создание JSXGraph-элемента, ссылающегося
  на JS-переменные родителей`. Таблица по `command.name` (как
  `lib_commands.COMMAND_REGISTRY`, но в обратную сторону).
- `builder.py` — обход конструкции в порядке `level`/топосорта: для каждого
  независимого — интерактивный вход (§4.3), для каждой команды — `command_map`
  (или фолбэк, §4.5), для каждого элемента — стиль + подпись.
- `document.py` — сборка: `json` (board spec), `js` (фрагмент `JXG.JSXGraph.
  initBoard(...)` для встраивания), `html` (самодостаточная страница с CDN
  JSXGraph + MathJax). Бонус-таргет — формат Moodle-фильтра JSXGraph.
- `exporter.py` — оркестрация + отчёт о покрытии.

API: `scene.exportJSXGraph(filepath=None, *, options=None, **kwargs)`.

### 4.5 Graceful degradation + отчёт о покрытии (обязательно)
JSXGraph покрывает распространённые конструкторы, но **не все ~291 команды**.
Стратегия:
- **Live-команды** (есть нативный аналог) → интерактивные, пересчёт в браузере.
- **Static-fallback** (нет аналога) → вычисляем в Python и эмитим как
  *фиксированные координаты* (точка/полилиния), которые **не двигаются** при
  драге. Если у такого элемента предок — анимируемый независимый, он не будет
  отслеживать — это честно логируем.
- На экспорте печатать сводку (как диагностика unsupported-команд в парсере):
  «N элементов live, M статических», с перечислением статических.

### 4.6 Покрытие команд — что брать в Фазу 1
«Школьно-олимпиадное ядро», покрывающее основную массу конструкций:
Point, Midpoint/Center, Segment, Line, Ray, Vector, Circle(center+point /
center+radius), Intersect (line∩line/∩circle/circle∩circle), Perpendicular &
Parallel line, PerpendicularBisector, AngleBisector, Polygon, Angle (+прямой
угол), Tangent, плюс Slider/Boolean. → ~30–40 команд = большинство импортируемых
GGB-файлов.
- **Фаза 2:** Ellipse/Hyperbola/Parabola (`board.create('conic'/'ellipse'/...)`),
  function graph (`functiongraph`), часть пересечений.
- **Фаза 3:** Moodle-embed, проигрывание keyframes как анимации слайдеров
  (JSXGraph умеет `setAnimation`), полировка.

### 4.7 Риски / открытые решения (вынести на согласование)
- **Полнота `command_map`** — главный scope-вопрос. Старт с ядра §4.6.
- **Выбор ветви пересечений / индексация** у JSXGraph иные, чем у нас → seed
  начальными координатами; задокументировать возможные расхождения ветвей.
- **Параметризация glider ≠ наш `tparam`** (JSXGraph хранит позицию точкой, не
  углом) → инициализировать координатами.
- **Численные расхождения**: live-команды должны совпадать; static-fallback не
  двигается. Документировать.
- **Подписи**: `name` + `withLabel`, LaTeX через `useMathJax` board-флаг;
  текст — из `resolve_label_text`.
- **Координаты**: JSXGraph работает прямо в MU c `boundingbox` — конвертация px
  нужна только для размеров стиля (size/strokeWidth), не для геометрии.

### 4.8 Тесты
- Юнит на `command_map`: малая DSL-конструкция (A, B free; M=Midpoint;
  c=Circle(A,B); P=Intersect) → ожидаемые `create('point'...)`,
  `create('midpoint',[A,B])`, `create('circle',[A,B])`, `create('intersection',
  ...)`, корректные ссылки на переменные.
- Независимые → нужные интерактивные типы (point/glider/slider/checkbox).
- Отчёт о покрытии: сцена с неподдержанной командой → элемент помечен static,
  предупреждение залогировано.
- Режимы вывода json/js/html (валидный JSON; html содержит initBoard + CDN).
- (Опц.) headless-проверка через node + jsdom, если будет в CI.

### 4.9 Оценка
Высокая, фазами. Фаза 1 (ядро + входы + стиль + подписи + 3 режима вывода +
отчёт) — ~3–5 дней. Фазы 2–3 — инкрементально. Это самостоятельное направление,
дающее то, чего не может ни один «экспорт-в-картинку».

## 5. Accessible SVG — справка / отчёт (НЕ реализуем сейчас)

### 5.1 Зачем это вообще нужно
- **Юридически/институционально.** Доступность учебных материалов требуется
  WCAG 2.x, Section 508 (США), EN 301 549 (ЕС), ADA. Вузы/издатели всё чаще
  отклоняют недоступные материалы.
- **Технически.** Незрячие/слабовидящие читают через скринридеры; им нужен
  машиночитаемый текст и описание рисунка, а не картинка.
- **Наш разрыв.** В текущем SVG подписи — это **контуры Безье**, а не `<text>`:
  скринридер не получает *ничего*, поиск/копирование текста невозможны. То есть
  наш SVG сегодня для доступности = пустая картинка.

### 5.2 Что значит «accessible SVG» технически
- Корневой `<svg role="img">` + `aria-label`/`aria-labelledby`.
- `<title>` (короткое имя) и `<desc>` (развёрнутое описание) — попадают в
  `@alt`-эквивалент.
- Сохранение подписей как **настоящего `<text>`** (а не контуров).
- Структурные `<g>`-группы по элементам с подписями/ARIA.
- Продвинутый уровень (экосистема PreTeXt/**PreFigure**/**diagcess**): послойное
  «исследование» диаграммы скринридером, озвучивание (sonification), MathML для
  формул.

### 5.3 Почему это *наш* потенциальный козырь
PreFigure-авторы пишут описания диаграмм **вручную**. У нас есть **семантика
конструкции**: мы знаем «отрезок AB», «окружность с центром O через A», «угол ABC
= 90°». Значит можем **авто-генерировать** альт-текст/`<desc>` из графа +
`resolve_label_text`. Это то, что отличает нас от любого скриншот-инструмента.

### 5.4 Эскиз реализации (на будущее, НЕ сейчас)
- Нужен **нативный SVG-эмиттер** (а не Cairo-контуры): рисует геометрию как
  `<circle>/<line>/<path>` и подписи как `<text>`; инъектит `title/desc/aria`.
  Архитектурно — близнец TikZ-эмиттера, но цель = SVG-DOM.
- **Генератор описаний**: обход графа (типы элементов + входы + значения) →
  фразы на естественном языке (шаблоны, при желании — локализуемые).
- Возможная интеграция с diagcess для послойного исследования.
- **Решение отложено** по указанию заказчика; здесь — только обоснование и эскиз.

## 6. EMF / Asymptote / reveal.js — заметки (НЕ трогаем)

### 6.1 EMF / EMF+ (редактируемый вектор для MS Office)
- **Контекст спроса:** вставка в Word/PowerPoint с возможностью «разгруппировать
  в нативные фигуры».
- **Важная оговорка:** современный Office (2016/365) **импортирует SVG нативно** →
  наш SVG уже закрывает большинство Office-сценариев. EMF нужен в основном для
  старого Office или ради ungroup-в-фигуры.
- **Тех. барьер:** нет хорошего чистого Python-писателя EMF (pyemf — старый,
  py2). Реалистичный путь — конвертация SVG→EMF через внешний Inkscape/LibreOffice
  CLI. Низкий приоритет; вернуться при явном спросе.

### 6.2 Asymptote (ещё один LaTeX-смежный векторный язык)
- TikZ уже обслуживает эту аудиторию; Asymptote силён в 3D и сложной
  программной графике.
- Если делать — **переиспользовать паттерн TikZ-экспортёра** (эмиттеры
  `draw()/dot()/label()`); ROI ниже текущего TikZ. Заметка на будущее.

### 6.3 reveal.js (HTML-слайды с нашими анимациями)
- Это **не новый рендер**, а слой упаковки/презентации (аналог manim-slides):
  HTML-шаблон, встраивающий наши MP4/GIF/animated-SVG/JSXGraph с разбиением на
  слайды.
- **Зависит от §2/§3/§4.** Когда они готовы — reveal.js-экспортёр сводится к
  HTML-шаблону. Отложить.

## 7. Приоритезация и последовательность

| # | Формат | Тракт | Сложность | Переиспользует | Приоритет |
|---|--------|-------|-----------|----------------|-----------|
| 1 | **PDF / EPS** | статический | низкая | `svg_parser.py` | сделать первым |
| 2 | **GIF / WebM / MOV** | рендер | низкая | `manim.config.format` + keyframes | следом |
| 3 | **animated SVG** | статический ×N | средняя/высокая | keyframe-цикл + static-рендер + граф | после 1–2 |
| 4 | **JSXGraph / JS** | новый | высокая (фазы) | граф + `get_independents()` + `resolver` | флагман, отдельно |
| 5 | accessible SVG | новый | — | семантика + `resolve_label_text` | только справка (§5) |
| 6 | EMF / Asymptote / reveal.js | — | — | — | только заметки (§6) |

**Рекомендуемый порядок:** PDF/EPS → GIF → animated SVG → JSXGraph (фазами),
параллельно с накоплением требований к accessible SVG.

**Общий принцип:** §1–§2 — «гигиена» (ожидаемые форматы, почти бесплатны на
существующих трактах). §3–§4 — настоящие дифференциаторы, монетизирующие то, что
есть только у нас: семантический граф конструкции и систему keyframes.
