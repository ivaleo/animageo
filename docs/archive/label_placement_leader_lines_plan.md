# P2-A — Выноски (leader lines): мини-план реализации

> Статус: **в бэклоге** (заказчик: «выноски с линиями пока не реализуем»). Этот
> документ — готовый к реализации дизайн, чтобы при зелёном свете собрать фичу
> без новой стадии проектирования. Закрывает оставшиеся `ok`-кейсы авторазмещения
> (совпадающие/плотные точки: E15/E16, T/E/S, T/K — round-13 Hermes), которые
> механизмом «поставить рядом» неустранимы (нет места: 0/72 свободных направлений).

## 1. Что это и когда нужно

Когда подпись **физически некуда поставить близко без наложения** (доказано
замером: scene19 `A_1=A_7` не имеет свободного места до +40px; cl_test5 `T/E/S`
у одной точки), единственное корректное решение — **отвести подпись в свободную
зону и соединить тонкой линией-выноской** с её объектом. Так сохраняется и
читаемость (нет наложения), и привязка (линия указывает, к чему относится).

Не применять, когда место есть — выноска засоряет чертёж. Это **крайняя ступень
деградации**, а не первичная стратегия.

## 2. Детекция: какие подписи требуют выноску

Переиспользуем то, что солвер УЖЕ знает. После `compute_label_layout` для каждой
static-подписи известны: финальная позиция, размер bbox, препятствия. Кандидат на
выноску, если выполняется хотя бы одно (за конфиг-порогами):

1. **Остаточное наложение** — финальная позиция всё ещё пересекает геометрию
   (солвер не нашёл свободного места в пределах нудж-капа). Это ровно стук-кейсы
   `0/72 free`. Проверка: `_candidate_has_overlap(center, half_w, half_h, …)` по
   полному (не culled) набору на финальной позиции.
2. **Наложение подпись-подпись** — пара near-coincident подписей, которые
   `_declutter_pass` не смог развести (нет места). Проверка: остаточный bbox-overlap
   после declutter.
3. **(опц.) Перерастянутость** — `|offset|` превысил порог (подпись «улетела» далеко
   ради свободы). Менее приоритетно; основной триггер — (1)/(2).

Порог включения по плотности (research §5, ~12.5%) — как глобальный гейт: выноски
только если доля «стуковых» подписей значима, иначе оставляем overplot.

API: `LabelPlacement` получает поле `leader: Optional[LeaderSpec]` (None = обычная
подпись). Конфиг `label_overflow: 'overplot'(деф)|'leader'|'hide'` (P1-B). При
`'leader'` детекция включается.

## 3. Размещение вынесенной подписи (boundary labeling)

Для подписей-кандидатов:

1. **Целевая зона** — ближайшая к якорю **свободная** область за пределами плотного
   узла. Алгоритм: луч от центра плотного кластера через якорь наружу; точка, где
   bbox подписи становится overlap-free (можно переиспользовать
   `_push_clear_along` с большим капом, которого нет в обычном режиме). Либо —
   к границе вьюпорта (классический boundary labeling) для самых тяжёлых сцен.
2. **Sort-and-stack** для бескроссинговости (research §8.6, Bekos): подписи,
   вынесенные к одной стороне, упорядочиваются по углу/координате якоря и
   складываются стопкой с равным шагом — порядок стопки = порядок якорей ⇒ линии
   не пересекаются. `O(n log n)`.
3. **Устранение оставшихся пересечений** локальной перекоммутацией соседних
   подписей в стопке (swap, если уменьшает суммарную длину/пересечения).

Это отдельный проход `_leader_layout_pass(scene, labels, result, …)` ПОСЛЕ
declutter; мутирует `result`, проставляя `LeaderSpec`.

## 4. Модель данных

```python
@dataclass
class LeaderSpec:
    anchor_pt: tuple      # точка объекта (scene MU) — куда указывает линия
    attach: tuple         # точка на КРАЮ bbox подписи, откуда выходит линия
    style: dict           # цвет (= цвет подписи), толщина, опц. стрелка
```
`LabelPlacement.leader = LeaderSpec | None`. `attach` вычисляется как пересечение
отрезка (центр_подписи → anchor_pt) с bbox подписи — линия начинается у кромки, не
из центра текста.

## 5. Рендеринг — по одному месту на бэкенд

Линия рисуется тем же стилем-резолвером, что и геометрия; z-index ниже текста,
выше заливок (новый тир `Z_LEADER` между `Z_FILL` и `Z_LABEL` в `constants.py`).

- **SVG** (`parsers/svg_parser.py`): Cairo `move_to/line_to` от `attach` к
  `anchor_pt`, тонкая (0.5–0.75pt), цвет подписи.
- **manim** (`animageo.py::_make_label`/`_place_label`): `Line(attach, anchor_pt)`
  как часть label VGroup, чтобы двигалась с подписью в анимации.
- **TikZ** (`exporters/tikz/emitters.py`): `\draw[very thin, <color>] (attach) -- (anchor);`
  рядом с `\node` подписи.
- **JSXGraph** (`exporters/jsxgraph/…`): `board.create('segment'/'line', …)` или в
  spec — новый элемент `leader` (точки фиксированные, не draggable).

Все четыре читают `LeaderSpec` из `LabelPlacement` — единый источник.

## 6. Конфиг (в `rendering.label_placement` / schema)

| Ключ | Деф | Назначение |
|---|---|---|
| `label_overflow` | `'overplot'` | `'leader'` включает детекцию+вынос; `'hide'` прячет низкоприоритетные |
| `leader_density_gate` | `0.125` | доля стуковых подписей, выше которой включаются выноски |
| `leader_width_px` | `0.6` | толщина линии |
| `leader_arrow` | `false` | стрелка у якоря |
| `leader_target` | `'free'` | `'free'` (ближайшая свободная зона) / `'boundary'` (поля) |

Дефолт `'overplot'` ⇒ byte-identical, фича строго opt-in.

## 7. Тесты

- Детекция: на cl_test5/test6 совпадающих точках `leader is not None`; на разреженной
  сцене — `None`.
- `attach` лежит на кромке bbox; отрезок attach→anchor не пересекает другие подписи
  стопки (бескроссинговость).
- Sort-and-stack: для N якорей на одной стороне линии не пересекаются.
- Экспортеры: SVG/TikZ/JSXGraph emit-ят соединитель (есть `\draw`/segment/line).
- Анимация: leader входит в label VGroup, двигается синхронно (dynamic tracker).

## 8. Объём и риски

- **Объём:** средний-крупный. Ядро (детекция + free-target + sort-stack + модель)
  ~1 проход + dataclass. Рендер — 4 точечные вставки. Тесты — новый файл.
- **Риск:** низкий для механизма (новый opt-in проход, дефолт off, не трогает
  текущие 0-bad раскладки). Основная работа — аккуратный рендер в 4 бэкендах и
  бескроссинговость стопок.
- **Зависимости:** `Z_LEADER` в `constants.py`; `LeaderSpec` в `label_placement.py`;
  по одной правке в svg_parser / animageo / tikz/emitters / jsxgraph.
