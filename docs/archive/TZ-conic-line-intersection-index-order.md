# ТЗ: индекс пересечения `Intersect(коника, …, n)` не сохраняет порядок GeoGebra (вершина «прыгает» на другую ветвь)

**Кому:** команде разработки библиотеки `animageo`
**Модуль:** `animageo/geo/construction.py` (`_intersect_points_order`, `apply`), `animageo/geo/lib_commands.py` (`intersect_Kli` / `intersect_KKi` / `intersect_KCi`, `order_points_by_reference`, `res_by_index`)
**Версия, на которой проводился анализ:** `animageo == 1.4.4` (локальная editable-установка)
**Приоритет:** средний (нарушение непрерывности `Intersect` — реальный баг корректности; проявляется как одиночный «прыжок» вершины на вырожденных углах, см. §1a)
**Автор разбора:** диагностика по обращению владельца сервиса animageo-web

> **1a. Уточнение области (важно, добавлено после доп. проверки).** На реальном
> примере `gGqlphuIE_0` прогон свободной точки `D` по эллипсу с шагом 1° (360
> шагов) даёт разрыв `C` **ровно на одном угле** — 270°, где прямая `h` строго
> горизонтальна (нормаль пересекает ось). Это **изолированный transient**
> (мера-ноль по углу), а не персистентный обмен ветвями на диапазоне. Поэтому
> баг реален (нарушает контракт непрерывности `Intersect`), но при статическом
> рендере «ломает» вершину только если геометрия оказалась ровно на вырожденном
> угле. Это **НЕ подтверждено** как причина конкретной жалобы владельца сервиса
> на устойчивое смещение `C` — та требует диагностики по живому (не сохранённому)
> состоянию редактора. Тем не менее фикс ниже стоит сделать: непрерывность
> `Intersect` — правильное поведение (как в GeoGebra).

---

## 1. Краткая суть

Для команды `Intersect(объект, объект, n)` с явным индексом `n` (и для мульти-выхода `Intersect(...) -> A, B`) GeoGebra присваивает индекс каждой из двух точек пересечения по **непрерывности** (continuity): при первом построении фиксируется, какая точка «первая», а какая «вторая», и дальше это соответствие **удерживается** при движении зависимостей. Индекс — это стабильная *ветвь*, а не «какая точка сейчас левее».

В `animageo`:

- **порядок пересечений сохраняется только когда один из объектов — `Circle`** (`_intersect_points_order` возвращает подсказку `points_order` исключительно для окружностей, construction.py:741-747);
- для **общей коники** (эллипс/гипербола/парабола) `_intersect_points_order` возвращает `None`, и `intersect_Kli` / `intersect_KKi` / `intersect_KCi` откатываются на **фиксированную геометрическую сортировку** (для коника×прямая — «по возрастанию параметра `t` вдоль направления прямой», lib_commands.py:831-837).

Фиксированная сортировка **не является непрерывной**: при движении свободных точек прямая поворачивается, и в некоторый момент «первая по `t`» и «вторая по `t`» точки **меняются местами** — индексы `1↔2` переворачиваются. В результате производная вершина, определённая как `Intersect(коника, прямая, 2)`, **скачком перепрыгивает** на другую точку эллипса, тогда как GeoGebra держит её на прежней ветви.

**Требуется:** для пересечений с участием коники (и вообще любого не-`Circle` пути) присваивать индексы так же стабильно, как это делает GeoGebra — так же, как уже сделано для окружностей.

## 2. Воспроизведение (ground truth)

**Пример:** https://animageo.ru/shared/gGqlphuIE_0 — «куб и тетраэдр». Базовая тройка вершин `A, B, C` вписана в эллипс `c`, где

```
c = Ellipse(A₁, B₁, C₁)          # коника (эллипс), не окружность
C = Intersect(c, h, 2)           # 2-я точка пересечения эллипса и прямой h
J = Intersect(c, h, 1)           # 1-я точка (та же прямая, тот же эллипс)
# прямая h зависит от свободных точек D = Point(c) и F = Point(c)
```

(`.ggb` доступен публично: `GET https://animageo.ru/api/shared/gGqlphuIE_0/ggb`.)

В **сохранённом** состоянии (`D.tparam ≈ 5.9998` рад) animageo считает `C = (1.845, −2.990)` — совпадает с GeoGebra попиксельно. Баг проявляется при **другом** положении `D`: тогда animageo берёт **другую ветвь**, чем GeoGebra, и `C` встаёт не на место.

**Минимальный скрипт-воспроизведение** (крутим свободную точку `D` по эллипсу, смотрим `C`):

```python
import math, logging; logging.disable(logging.WARNING)
from animageo.animageo import AnimaGeoScene

scene = AnimaGeoScene()
scene.loadGGB("gGqlphuIE_0.ggb", generate_stubs=False)
geo = scene.geo
D = geo.element("D")

def C():
    d = geo.objectByName("C").data
    return (round(float(d.x), 2), round(float(d.y), 2))

prev = None
for i in range(0, 73):
    t = i / 72 * 2 * math.pi
    D.tparam = t
    geo.rebuild(full=True)
    c = C()
    if prev and ((c[0]-prev[0])**2 + (c[1]-prev[1])**2) ** 0.5 > 1.0:
        print(f"t={math.degrees(t):.0f}°  C JUMPED  {prev} -> {c}")
    prev = c
```

**Фактический вывод:**

```
t=270°  C JUMPED  (7.07, -2.18) -> (-1.13, -2.0)
```

При переходе `260° → 270°` точка `C` **прыгает на 8.25 единиц** через весь эллипс, а `J` синхронно уезжает в противоположный конец — то есть `C` и `J` **обменялись ветвями**. Непрерывная (как в GeoGebra) привязка индекса такого разрыва бы не дала: обе точки должны плавно скользить по эллипсу.

> Диагностический признак: `Intersect(коника, прямая, n)` по контракту GeoGebra — **непрерывная** функция входных данных. Любой скачок выхода при плавном входе = нарушение контракта.

## 3. Корневая причина

### 3.1. `_intersect_points_order` знает только `Circle` (construction.py:729-768)

```python
first_two = input_data[:2]
circle_index = None
for i, data in enumerate(first_two):
    if isinstance(data, Circle):      # ← только Circle
        circle_index = i
        break
if circle_index is None:
    return None                       # ← Conic/Ellipse: подсказки порядка НЕТ
```

Для эллипса `data` — это `Conic`, `isinstance(data, Circle)` ложно → `points_order = None`.

### 3.2. Индексные обёртки без подсказки берут фиксированную сортировку

`intersect_Kli` (коника×прямая, lib_commands.py:849-851), `intersect_KKi` (коника×коника, :930), `intersect_KCi` (коника×дуга, :964) — все принимают `points_order`, но при `None` `res_by_index` → `order_points_by_reference(res, None)` возвращает `res` **как есть**, а `res` уже отсортирован фиксированно. Для коника×прямая (lib_commands.py:831-837):

```python
# Sort ascending: smaller-t point first, regardless of sign(A).
t1, t2 = sorted(((-B - sq) / (2 * A), (-B + sq) / (2 * A)))
```

Комментарий в коде утверждает, что это «Matches GGB's index 1 = leftmost along line direction» — **это неверно**: GeoGebra не переупорядочивает точки геометрически на каждом пересчёте, он удерживает исходную ветвь по непрерывности. «Leftmost along line» и «стабильная ветвь» совпадают лишь до первого разворота прямой.

### 3.3. Итог

Механизм сохранения порядка (`points_order` → `order_points_by_reference`), уже работающий для окружностей, **не подключён для коник/локусов/функций**. Любая производная точка `Intersect(коника, …, n)` рискует оказаться на неверной ветви, как только геометрия отойдёт от сохранённого состояния (интерактив, анимация, повторное построение из другого кадра).

## 4. Что требуется сделать

Дать индексам пересечений с коникой (и вообще любым не-`Circle` объектом) **стабильную, GeoGebra-совместимую** привязку. Рекомендуемое направление (по возрастанию предпочтительности):

**Вариант A — привязка по кэшированным координатам выходных точек (наиболее точный для загруженного `.ggb`).**
В момент `apply()`/`rebuild` у выходных элементов (`C`, `J`) уже есть распарсенные из XML координаты — это ровно та ветвь, которую зафиксировал GeoGebra. Использовать их как `points_order`/референс: каждую вычисленную точку пересечения матчить к ближайшей *прежней* позиции соответствующего выхода. Это воспроизводит присвоение GeoGebra для статической загрузки **и** даёт устойчивость при пересчёте.

**Вариант B — непрерывность по предыдущему кадру (для анимации).**
При пересчёте (`rebuild`, покадровая анимация) сопоставлять новые точки пересечения с *предыдущими* позициями выходов (nearest-match), а не сортировать геометрически. Тогда ветвь удерживается по непрерывности — как в GeoGebra.

**Минимально:** расширить `_intersect_points_order`, чтобы для не-`Circle` входов он возвращал референс на основе текущих/кэшированных позиций выходных точек команды (`command_original.outputs`), а не только определяющих точек окружности. Обёртки `intersect_Kli/KKi/KCi` уже принимают `points_order` — достаточно, чтобы он перестал быть `None`.

### Критерий приёмки

1. Скрипт из §2 на `gGqlphuIE_0.ggb`: при полном обороте `D` вокруг эллипса позиция `C` меняется **непрерывно** — ни одного скачка `> 1.0` ед. между соседними шагами `≤ 5°`.
2. Для сохранённого состояния `C`, `J`, `A`, `B` остаются попиксельно равны GeoGebra-кэшу (регресс не допускается — сейчас там совпадение).
3. Аналогичная стабильность для `Intersect(коника, коника, n)` (`intersect_KKi`) и `Intersect(коника, дуга, n)` (`intersect_KCi`).
4. Поведение для `Circle`-пересечений не меняется.

## 5. Область (scope) и связи

- Это **отдельный** баг от уже исправленной в 1.4.4 анимации точек на конике (`tparam_point`, ТЗ `TZ-conic-locus-point-keyframe-animation.md`): там движется точка **на** конике, здесь — производная точка **пересечения** с коникой.
- Затрагивает и статический рендер (вершина не на месте после интерактива/повторного построения), и анимацию (если анимируется зависимость прямой/коники — вершина `Intersect(...)` будет дёргаться между ветвями).
- Сторона `animageo-web` повлиять не может: порядок пересечений целиком внутри `rebuild` библиотеки. Веб лишь загружает `.ggb` и вызывает пересчёт.
