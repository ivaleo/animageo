# ТЗ: анимация точки, привязанной к конике/локусу/функции, не работает (кадры «замерзают»)

**Кому:** команде разработки библиотеки `animageo`
**Модуль:** `animageo/geo/construction.py` (`get_independents`), `animageo/keyframes.py` (`_parse_value`), `animageo/parsers/ggb_parser.py` (готовые `get_tparam_from_point_and_*`)
**Версия, на которой проводился анализ:** `animageo == 1.4.3` (локальная установка)
**Приоритет:** высокий (полностью ломает экспорт анимации целого класса конструкций)
**Автор разбора:** диагностика по обращению владельца сервиса animageo-web

---

## 1. Краткая суть

Если в анимации движется **точка, лежащая на пути**, и этот путь — **коника (эллипс/гипербола/парабола)**, **локус** или **функция** (а не окружность/отрезок/прямая/луч), то экспортированное видео получается **полностью статичным**: ничего не движется, хотя ключевые кадры содержат корректно меняющиеся координаты точки.

Причина — точки на такой траектории классифицируются как `tparam_point` с `constraint = 'unknown'`, и во всей цепочке (детект независимых элементов → парсинг значения кадра → выбор режима интерполяции) конику/локус/функцию **не обрабатывают**, хотя нужные математические хелперы в библиотеке **уже есть** (`get_tparam_from_point_and_conic`, `get_tparam_from_point_and_locus` в `ggb_parser.py`), просто не подключены к анимационному пути.

**Требуется:** сделать точки на конике/локусе/функции полноценно анимируемыми — так же, как уже работают точки на окружности/прямой/отрезке/луче.

---

## 2. Воспроизведение и пример (ground truth)

**Пример:** https://animageo.ru/shared/tYwHUgEyock — «вписанный шестиугольник». Экспортированное MP4 (80 кадров, 5.3 с) **попиксельно статично** (кадры 0/40/79 идентичны), хотя в таймлайне движется точка `D`.

**Геометрия** (`.ggb` доступен публично: `GET https://animageo.ru/api/shared/tYwHUgEyock/ggb`):
- свободные точки `A`, `B`, `C` (скрыты) задают эллипс `c = Ellipse(A, B, C)`;
- `D = Point(c)` и `G = Point(c)` — точки **на конике** `c` (тип `ELLIPSE`);
- всё видимое (инцентр/центр `E`, `F`, шестиугольник `L,M,N,O,…`, треугольник `P,Q,R`, полигоны, отрезки) — **производное** от `A,B,C,D,G`.

**Ключевые кадры** (реальный `TimelineData` из БД сервиса): координаты `D` меняются от кадра к кадру:
`[6.54, −1.04] → [9.85, −0.38] → [11.13, 1.05] → [9.37, 2.84] → [2.45, 0.31] → [6.54, −1.04]`. `A,B,C,G` — постоянны. То есть **данные анимации корректны**, движется только `D` вдоль эллипса.

**Минимальное воспроизведение на стороне библиотеки** (без сервиса):

```python
from animageo.geo.construction import Construction
from animageo.parsers import ggb_parser
from animageo.ui import GeoStyle

geo = Construction()
ggb_parser.load(geo, GeoStyle().export, "hex.ggb")

inds = geo.get_independents()
print(inds["D"])
# → {'type': 'tparam_point', 'constraint': 'unknown', ...}   ← БАГ: должно быть 'conic'/'ellipse'

# при этом нужный хелпер уже умеет считать параметр:
from animageo.parsers.ggb_parser import get_tparam_from_point_and_conic
print(get_tparam_from_point_and_conic(geo.element("D").data, geo.element("c").data))
# → 4.686...   ← корректный tparam эллипса
```

**Как это ломает экспорт (сторона animageo-web, для контекста).** Веб перед `play_keyframes` конвертирует захваченные `[x, y]` каждой `tparam_point` обратно в `tparam`. Конвертер (`app/services/animation_export.py:788-823`) поддерживает только `Circle/Segment/Line/Ray`; для коники `tparam` не считается → `del vals["D"]` — единственный движущийся элемент **выбрасывается из кадров**. Остаются лишь постоянные `A,B,C` → у `play_keyframes` нет ни одного меняющегося значения → на каждый интервал `self.wait(duration)` → видео «замерзает».

> Веб вынужден дублировать эту конвертацию только потому, что библиотека не предоставляет единого API «координаты → tparam для любого пути» и не сообщает тип пути через `get_independents`. Мы хотим убрать этот дубль на стороне веба (см. §4, вариант A) — но для этого нужна доработка библиотеки.

## 3. Корневая причина (три разрыва в библиотеке)

### 3.1. `get_independents()` не распознаёт конику/локус/функцию как constraint
`animageo/geo/construction.py:465-490`. Для `tparam_point` определение `constraint` перебирает только `Circle / Segment / Ray / Line`:

```python
if isinstance(inp_data, Circle):  constraint = 'circle'; break
elif isinstance(inp_data, Segment): constraint = 'segment'; break
elif isinstance(inp_data, Ray):     constraint = 'ray'; break
elif isinstance(inp_data, Line):    constraint = 'line'; break
# ← нет ветки Conic / Locus / Function
```
→ для точки на конике `constraint = 'unknown'`, и потребитель не знает ни типа пути, ни объекта пути.

### 3.2. `_parse_value()` для `unknown` молча выбирает линейную интерполяцию
`animageo/keyframes.py:317-330`. Режим выбирается так:
```python
constraint = info.get('constraint', 'line')
kind = 'tparam_circle' if constraint == 'circle' else 'tparam_linear'
```
Для замкнутой коники (эллипс) нужен **циклический** режим с wrap по `2π` (как у окружности), а `'unknown'` → `'tparam_linear'` — это неверная семантика интерполяции даже если tparam всё-таки передать.

### 3.3. Готовые хелперы не подключены к анимационному пути
`animageo/parsers/ggb_parser.py` уже содержит:
- `get_tparam_from_point_and_conic` (`:223`) — покрывает `CIRCLE / ELLIPSE / HYPERBOLA / PARABOLA`;
- `get_tparam_from_point_and_locus` (`:265`) — ближайшая точка ломаной локуса;
- плюс `_circle/_line/_segment` (`:202/208/214`).

Они используются при **загрузке** (`.ggb` → construction), но **не** переиспользуются ни в `get_independents`, ни как публичный API «координаты → tparam», которым мог бы пользоваться экспорт анимации.

## 4. Рекомендуемое исправление

### Вариант A (предпочтительно) — библиотека сама принимает координаты для `tparam_point`
Разрешить в ключевом кадре для `tparam_point` значение `[x, y]` (не только `{"tparam": …}`). Внутри `_parse_value`/apply проецировать координаты на путь и считать `tparam` **единым** механизмом для всех типов пути (circle, segment, line, ray, **conic**, **locus**, **function**), переиспользуя существующие `get_tparam_from_point_and_*`. Тогда клиент (веб) просто передаёт захваченные координаты любой подвижной точки, а вся математика — в библиотеке. Это убирает дублирующий и неполный конвертер на стороне веба.

Требования к варианту A:
- проекция должна корректно работать и для точки, чуть смещённой с пути (интерполированные/захваченные координаты могут не лежать строго на конике);
- для замкнутых путей (окружность, эллипс) — циклическая интерполяция с выбором кратчайшей дуги (уже есть `direction: 'short'`); для незамкнутых (парабола, прямая, отрезок, ветвь гиперболы, функция) — линейная по параметру.

### Вариант B (минимально-инвазивно) — если менять формат кадра нежелательно
1. §3.1: расширить определение `constraint` в `get_independents` — распознавать `Conic` (с уточнением `circle/ellipse/hyperbola/parabola` по `conic.type`), `Locus`, `Function`; возвращать также ссылку на объект пути.
2. §3.2: в `_parse_value` выбирать `tparam_circle` (циклический) для окружности **и эллипса** (и вообще замкнутых коник), `tparam_linear` — для остальных; убрать «немой» дефолт `'line'` для `unknown`.
3. Экспонировать публичный метод, например `Construction.tparam_from_coords(point_name, coords) -> float | None`, диспетчеризующий на существующие `get_tparam_from_point_and_*` по типу пути. Тогда веб заменит свой неполный конвертер одним вызовом.

В обоих вариантах ядро математики уже написано — работа в основном «проводка» (wiring) + тесты.

---

## 5. Критерии приёмки

1. `geo.get_independents()["D"]` для точки на эллипсе возвращает осмысленный `constraint` (не `'unknown'`) и позволяет получить `tparam`.
2. `play_keyframes` для конструкции из §2 даёт **движущееся** видео: `D` едет по эллипсу, производная геометрия (шестиугольник, треугольник `P,Q,R`, отрезки) пересчитывается на каждом кадре.
3. Регресс-тест: точка на **эллипсе** и точка на **локусе** анимируются между двумя ключевыми кадрами (проверить, что интерполятор создаётся и значения `tparam` меняются). Для замкнутой коники — интерполяция идёт по кратчайшей дуге и корректно wrap-ится через `2π`.
4. Точки на окружности/прямой/отрезке/луче продолжают работать как раньше (без регрессии).
