# ТЗ: авторазмещение подписей должно учитывать отметки углов как препятствия

**Кому:** команде разработки библиотеки `animageo`
**Модуль:** `animageo/label_placement.py` (механизм авторазмещения подписей)
**Версия, на которой проводился анализ:** `animageo == 1.4.2` (локальная установка)
**Приоритет:** средний (визуальное качество экспортируемых сцен/анимаций)
**Автор разбора:** диагностика по обращению владельца сервиса animageo-web

---

## 1. Краткая суть

При авторазмещении (`overlay.label_placement.enabled = true`) подпись точки может оказаться в том секторе вокруг точки привязки, где нарисована **отметка угла** (квадратик прямого угла или дуга), вместо свободного сектора без отметок. В результате отметка угла оказывается «в проходе» между подписью и её точкой.

Даже если подпись и отметка **не пересекаются** геометрически, отметка создаёт визуальное препятствие: читателю труднее сопоставить, что подпись принадлежит именно этой вершине, потому что на «линии взгляда» между подписью и точкой стоит маркер угла.

**Требуется:** при работе механизма авторазмещения находить наиболее свободное от отметок углов пространство рядом с точкой привязки и располагать подпись там. Отметки углов (включая квадрат прямого угла) должны учитываться как полноценные препятствия. Если свободного сектора нет — деградация graceful (выбрать наименее плохой вариант, как сейчас).

## 2. Воспроизведение и пример (ground truth)

**Пример:** https://animageo.ru/shared/-BJOgXWBsLU — анимация поворота треугольника с вписанной окружностью.

**Геометрия конструкции** (`.ggb` доступен публично: `GET https://animageo.ru/api/shared/-BJOgXWBsLU/ggb`):
- треугольник `A`, `B`, `C`, полигон;
- вписанная окружность, инцентр `D`;
- точки касания `E`, `F`, `G` на сторонах;
- радиусы `k`, `l`, `m` от `D` к точкам касания;
- прямые углы `β₂ = Angle(C, E, D)`, `β = Angle(A, F, D)`, `β₁ = Angle(B, G, D)` — в каждой точке касания радиус перпендикулярен стороне, рисуется маркер прямого угла (квадратик).

**Симптом (подтверждён по кадрам видео):**
- Кадр 0 (стартовый ключевой кадр): подписи `E`/`F`/`G` стоят **снаружи** стороны, в свободном секторе — корректно.
- Кадр 135 (**установившийся** конечный ключевой кадр — кадры 128…135 попиксельно идентичны, т.е. это статичное состояние, а не середина интерполяции): подпись `E` **зажата вплотную к квадратику-маркеру** во внутреннем секторе (между радиусом и стороной), при этом весь полупланарный сектор **снаружи** стороны пуст. Маркер стоит между вершиной `E` и её подписью.

То есть на части ключевых кадров авторазмещение выбирает сектор с отметкой угла, хотя рядом есть полностью свободный сектор.

> ⚠️ **Важно для воспроизведения.** На *реконструированном* стиле (builtin + рекомендованный пресет label_placement, `point_bisector=true`/`respect_current_position=true`) баг **не воспроизвёлся**: на полном повороте 0–360° и при выключении `point_bisector`/`respect_current_position`/самого `enabled` раскладка **всегда** выбирала свободный сектор (`cos(offset, D−вершина) ≈ −1`). Значит, на mark-side-выбор влияет именно **реальный (приватный) стиль конструкции** (`style_id = c6a79d9a-2339-46ae-9433-3964e3200fcf`) и/или конкретная деформация треугольника на ключевых кадрах, которую жёстким поворотом воспроизвести не удалось. Для точного воспроизведения и регресс-теста нужно запросить у владельца: **(1) style JSON** этого стиля и **(2) TimelineData (keyframes)** конструкции. Первый шаг работ — локализовать, какой именно левер (вес/флаг/геометрия) приводит к выбору сектора с маркером.

## 3. Корневая причина (анализ кода, 1.4.2)

**Отметки углов не входят в набор препятствий механизма размещения.**

`_collect_obstacles(scene)` (`label_placement.py:564`) собирает препятствия трёх видов: `segments`, `circles`, точечные `arc_pts`. Ветка для углов (`label_placement.py:602-607`):

```python
elif isinstance(d, geo.Angle):
    r_ang = min(np.linalg.norm(d.side1), np.linalg.norm(d.side2)) * 0.3
    pts = _sample_arc(d.vertex[:2], r_ang, d.start_angle, d.size, 12)
    for k in range(len(pts) - 1):
        segments.append((pts[k], pts[k + 1]))
        seg_dashed.append(dashed)
```

Проблемы:
1. **Квадрат прямого угла не регистрируется вообще.** Любой `Angle`, в т.ч. прямой, аппроксимируется обобщённой дугой из 12 точек. Реальный квадрат-маркер (рисуется в `_render_angle`, `animageo.py:2192-2219`, угловые точки на радиусе `right_angle_size_px / √2`) в препятствия не попадает.
2. **Радиус препятствия не совпадает с нарисованным.** Используется `0.3 · min(плечо)` в МЕ сцены, тогда как маркер рисуется на пиксельном радиусе (`right_angle_size_px/√2` для прямого, `arc_size_px` для дуги, с авто-масштабом `overlay.angle_radius`). Препятствие стоит не там, где видимая отметка.
3. **`angle_range` (minor/reflex) не учитывается** — взяты «сырые» `start_angle`/`size`; для рефлексных углов аппроксимация может оказаться вообще не на той стороне (рендер же учитывает это в `animageo.py:2152-2157`).
4. **Нет примитива столкновения с квадратом.** Коллизии считаются только против segments/circles/точек (`_score_candidate` `label_placement.py:1450`, `_candidate_has_overlap` `label_placement.py:496`). Облако плотности `_all_obstacle_points` (`label_placement.py:~710`) наследует ту же грубую аппроксимацию через `segments`.

**Следствие.** Ни солвер (`_solve_greedy`), ни repair/declutter-проходы, ни эвристики направления «не видят» маркер. Сторону выбирают: density-эвристика `_compute_preferred_dir`, биссектриса самого широкого зазора `_bisector_of_largest_gap`/`_incident_directions` (при `point_bisector`), и `respect_current_position` — **ни одна из них не штрафует сектор с отметкой угла**. Поэтому в некоторых конфигурациях подпись садится прямо в сектор с маркером.

> Замечание: подпись **самого угла** (его значение) ставится отдельным путём (`_collect_labels` → `compute_angle_label_center`, fixed-center по биссектрисе) и свой маркер обходит аналитически. Проблема касается подписей **других** элементов (точек-вершин), которые маркер не учитывают.

## 4. Требования

**Scope.** Изменения — только в механизме авторазмещения / снапшотах на ключевых кадрах. См. §6 «Вне рамок».

**R1. Регистрировать отметки углов как настоящие препятствия** в `_collect_obstacles` (и, как следствие, в облаке плотности):
- для **прямого угла** (right-mark) — реальный квадрат-маркер по 4 угловым точкам (как в `_render_angle`), на **действительном** радиусе `right_angle_size_px/√2` с учётом авто-масштаба `overlay.angle_radius` + `apply_to_right`. Для радиуса переиспользовать/повторить логику `_angle_render_label_radius_px` (`label_placement.py:1061-1082`), которая уже зеркалит рендер;
- для **обычной дуги** — дугу на действительном пиксельном радиусе (а не `0.3·min(плечо)`), с учётом `angle_range` (minor/reflex), как у рендера.

**R2. Предпочитать сектор без отметок углов.** При выборе направления/сектора для подписи точки-вершины: если рядом с точкой привязки есть сектор, свободный от маркеров, подпись должна располагаться там — так, чтобы маркер **не оказывался между подписью и её точкой**. Реализация на усмотрение команды, например:
- исключать/штрафовать сектор, занятый маркером, в `point_bisector`/`_bisector_of_largest_gap` (трактовать «плечи» отмеченного угла как занятый сектор);
- и/или добавить штраф в `_score_candidate` за попадание bbox подписи в сектор/радиус маркера (использовать новые препятствия из R1).

**R3. Детект прямого угла — как в рендере.** Считать угол «прямым» по тому же правилу, что `_render_angle` (`right_angle_marker`, иначе `np.isclose(angle, π/2)`, `animageo.py:2188-2190`), чтобы препятствие совпадало с реально нарисованной отметкой.

**R4. Без регрессий.** Там, где отметок углов нет или свободного сектора нет, размещение должно оставаться прежним. Существующие тесты `tests/test_label_placement_*.py` должны остаться зелёными. Если все секторы заняты — graceful degradation (наименее плохой вариант, как сейчас).

## 5. Критерии приёмки

1. На примере `shared/-BJOgXWBsLU` (с реальным стилем и keyframes): на **каждом** ключевом кадре для `E`/`F`/`G` подпись располагается в секторе **без** маркера — формально `cos(offset, D − вершина) < 0` (подпись снаружи, со стороны без радиуса/маркера), и bbox подписи не пересекает квадрат маркера и не лежит в его секторе.
2. Новый **регрессионный тест** в `tests/` (по образцу `test_label_placement_fp3.py` / `_r8` / `_r12`): минимальная сцена «точка на отрезке + прямой угол в этой точке»; assert, что (а) маркер присутствует в наборе препятствий из `_collect_obstacles`, (б) подпись садится в свободный сектор, а не в сектор маркера.
3. Все существующие тесты `label_placement` зелёные.
4. Желательно: до/после-рендер примера приложить к PR.

## 6. Вне рамок (важный контекст, НЕ делать в этой задаче)

- **Интерполяцию между ключевыми кадрами не трогать.** `LabelOffsetInterpolator.at` (`keyframes.py:116`) линейно интерполирует **вектор** смещения подписи между снапшотами. При повороте фигуры это (а) схлопывает длину смещения к середине интервала (замер: ~33px → ~4–11px) и (б) при большом повороте уводит подпись внутрь — поэтому **на промежуточных** кадрах подпись может наезжать на маркер. Это известно и сознательно **принимается** заказчиком как побочный эффект линейной интерполяции: задача — улучшить выбор **на ключевых кадрах**, а не сглаживать траекторию. (Если позже захотите убрать и промежуточный артефакт — отдельной задачей: интерполировать смещение в полярной форме «длина + угол по короткой дуге», по образцу уже имеющегося `_interpolate_angle` для `tparam_circle`.)

## 8. Релиз / интеграция

Web-сервис (`animageo-web`) запинен на `animageo == 1.4.2` (с PyPI), Docker-образ собирается через `pip install .`. Порядок выкладки после фикса:
1. bump версии: `animageo/pyproject.toml` + `animageo/__init__.py` + `CHANGELOG.md`;
2. `pyproject-build`, `twine check`, `twine upload`;
3. затем бамп пина `animageo==<new>` в `animageo-web/pyproject.toml`.

Нельзя бампить пин на версию, которой ещё нет на PyPI — иначе сломается сборка docker-образа web.
